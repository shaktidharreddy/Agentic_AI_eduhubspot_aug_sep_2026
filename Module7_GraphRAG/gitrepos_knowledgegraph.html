Verdict: feasible

Yes — and code suits a knowledge graph better than documents do.

The relationships you care about are already written down in code and config: calls, imports, table reads and writes, job → notebook, workflow → deployment. A parser extracts them exactly. In document GraphRAG an LLM has to guess them.

1

Code already is a graph

Functions call functions, files import files, jobs run notebooks, notebooks write tables, workflows deploy commits. Parsers read these edges, so there is no LLM guessing and almost no extraction cost.

2

Your best questions are multi-hop

"What breaks if I change this?", "Who writes this table?", "Is my fix in prod yet?" Each answer is a path through 3–6 nodes, often across repos. Vector-only RAG can't follow paths. A graph can.

3

You already know the stack

Neo4j, Cypher, OpenAI embeddings and a vector index are the same pieces as in your GVD course. What's new is a set of parsers, the GitHub API, and a sync job.

The design decision that matters mostDon't run document-style GraphRAG (an LLM extracting entities from text chunks) over code. Parse code deterministically, and use the LLM only for summaries, business concepts and writing the final answer.

Where the GitHub MCP fits

At question time → GitHub MCP

Use it for small, live lookups the chatbot makes while answering: the log of a failing job, the checks on an open PR, a file at HEAD. It is not built for bulk ingestion: it fetches one file per call, and a personal token gets 5,000 REST requests per hour.

At ingestion time → git + REST/GraphQL

A scheduled job clones each repo (one operation per repo, no per-file API calls) and pulls CI/CD metadata from the REST API: workflows, runs, environments, deployments, teams. Webhooks (push, workflow_run, deployment_status) keep it fresh.

Configured: GitHub's official MCP server, read-onlyThe remote endpoint https://api.githubcopilot.com/mcp/ with the headers X-MCP-Readonly: true and X-MCP-Toolsets: context,repos,git,actions,pull_requests,issues,orgs,users. That exposes 32 read-only tools, for example get_repository_tree, get_file_contents, search_code, list_commits and pull_request_read, plus actions_list, actions_get and get_job_logs for CI status. It has no deployment or environment tools, so deployment status comes from the REST API in the ingestion job. It replaced the deprecated @modelcontextprotocol/server-github, which had write tools and no read-only mode.

Prior art for this pattern: Sourcegraph's code graph (SCIP indexes), Aider's repository map (tree-sitter + PageRank), and research systems such as CodexGraph (an LLM agent querying a Neo4j code graph with Cypher) and RepoGraph.

Step by step

  1. Get read access and inventory the org

    Create a fine-grained, read-only token that is SSO-authorized for the org (see Roadmap → access checklist). List the repos and decide which to index; skip archived and forked repos.

  2. Clone, don't fetch file by file

    One clone per repo replaces thousands of per-file API calls. Keep the HEAD SHA: it is the "as of" for every answer and the starting point for incremental updates.

  3. Parse code into symbols

    One pass over each file's syntax tree gives classes, functions (the chunks), imports and raw call sites. Deterministic ids (repo:path::qualified_name) make every load repeatable.

  4. Find the tables each function reads and writes

    This is the data-platform layer. Spark API calls are found in the syntax tree, and SQL text (in spark.sql() or .sql files) is parsed with sqlglot. Names built at runtime are kept as patterns with dynamic = true.

  5. Resolve references, with a confidence on each

    Turn raw call text (self.load, cfg.read_config) into edges between real Function nodes:

    Call looks likeResolved toresolution / confidence
    helper() defined in the same fileThat functionexact · 1.0
    self.load()Method on the same class (or a base class)self · 0.95
    read_config() after from common.config import read_configThe function in common/config.py, or in another repo through PUBLISHED_FROMimport · 0.9
    df.write.saveAsTable(), requests.get()Library call: no Function edge (handled as a table access or Package use)—
    A unique name match elsewhere in the repoBest guessname-match · 0.4

    For near-perfect Python resolution later, generate SCIP indexes with scip-python and load their cross-references as resolution = 'exact'.

  6. Pull CI and deployment state from the API

    No parsing: CI status is WorkflowRun nodes and deployment status is Deployment nodes, both linked to the Commit they ran on.

  7. Load into Neo4j: constraints first, then batched MERGE

    The same run() helper as your course. MERGE on the id makes re-loading harmless, and deleting symbols that disappeared keeps the graph clean. That's the same "upsert + delete orphans" idea as Module 5P.

  8. Enrich: indexes, summaries, embeddings, derived edges

    Summaries go bottom-up (function → file → repo). Embed signature + docstring + summary. Derived edges (table lineage) and communities (Subsystem) are computed inside Neo4j.

Keep it fresh: two clocks

Code clock on every push to main, or nightly

  1. git fetch, then git diff --name-status <head_sha> origin/main.
  2. Re-parse only the changed files. MERGE their symbols and drop vanished ones.
  3. Refresh those files' outgoing edges, and re-resolve calls from files that import them.
  4. Re-summarise and re-embed only nodes whose content_hash changed.
  5. Recompute derived edges and fan-in/fan-out. Recompute communities weekly.
  6. Set Repository.head_sha and indexed_at.

Status clock every 10–15 min, or on webhooks

  1. Per repo: newest workflow runs on main, plus deployments and statuses per environment.
  2. MERGE WorkflowRun and Deployment nodes and their edges.
  3. Update roll-ups: Repository.ci_status, Environment.current_sha, Workflow.success_rate_30d.
  4. Delete runs older than the retention window (for example 30 days).
  5. Webhooks to subscribe to at org level: push, workflow_run, deployment, deployment_status.
Built: c8_refresh.py, scheduled in Windows Task SchedulerEvery 30 minutes (task codekg-refresh) it compares each repo's branch heads with git ls-remote, which takes about 50 s when nothing moved, and re-indexes only repos whose branch moved. Every night at 02:00 (codekg-refresh-nightly) it also re-reads CI, deployments, PRs, teams and new or removed repos for the whole org. A changed repo is re-extracted in memory, which takes seconds, so callers in importing files are re-resolved too. Only the delta is written: changed nodes are MERGEd, vanished ones DETACH DELETEd, and only changed edges are replaced. Summaries and embeddings stay on unchanged nodes. Tested by rolling cdp-genai-qrc-language-translation-be back 3 commits and letting the refresh bring it forward. The 17 changed files gave 138 nodes added, 238 rewritten and 346 edges created, and only 164 of 23,556 nodes were re-embedded. The repository came back node-for-node identical. Webhooks would need GitHub to reach this machine, so the status clock is the nightly re-read plus the chatbot's live github_live tool.
You've built this pattern beforeModule 5P's sync did three moves: embed only new or changed rows, refresh cheap metadata, delete orphans. The code clock does the same thing per file.

Guardrails

Answer rules

  • Cite permalinks pinned to the commit: …/blob/<sha>/path#L52-L97.
  • Say "as of <indexed_at>" for code answers and "as of <time>" for status answers.
  • When an edge has confidence below 0.7, say "probably", and offer the text-search fallback.
  • Never invent table, function or repo names. If the graph has no answer, say so.

Text-to-Cypher safety

  • A read-only Neo4j user, a query timeout, and an enforced LIMIT.
  • The schema (this page's graph) plus 10–20 example question → Cypher pairs in the prompt.
  • Run EXPLAIN first; on an error, retry once with the error message.
  • Prefer templates. Text-to-Cypher is the fallback, not the default.

Limitations, and what to do about them

None of these is a blocker, but each one changes how much you can trust certain answers.

Rough sizing (illustrative)

Graph size ≈ repos × files × (1 + symbols per file). For example, 40 repos × 250 files × 8 symbols ≈ 90,000 nodes and a few hundred thousand relationships. That's small for Neo4j.

Embeddings ≈ 90,000 × ~400 tokens ≈ 36 M tokens: typically well under $10 with a small embedding model. Summaries push a similar number of tokens through a small chat model, so they are the main cost, and they are incremental after the first run. Check current pricing; these numbers are illustrative, not measured on your org.

A second, separate knowledge graph for the cdp-de-* data engineering repositories: Snowflake objects and their lineage, Airflow DAGs, data products, source systems, and whether the SQL will actually deploy. It has its own ontology, its own Neo4j database and its own assistant; the app switches between the two graphs.

1

Lineage is written in the SQL

A view selects from tables, a dynamic table refreshes from a query, a procedure inserts into one table from another, a DAG task calls that procedure. A SQL parser reads every one of these edges; nothing has to be guessed by an LLM.

2

The questions are paths

"What feeds this view?", "What breaks if this table changes?", "Which DAG loads it, and when?", "Will my SQL deploy?" Each answer is a walk through objects, tasks, files and products, often across repositories. Vector search alone can't follow it.

3

Same stack as the GenAI graph

The same pipeline scripts, Neo4j, LiteLLM gateway, agent and web app. What's new is two parsers (Snowflake SQL and Airflow DAGs), the deployment replay, and an ontology built around Snowflake objects.

Why a separate ontology and database

Different things

The GenAI repos are apps (front ends, APIs, agents): functions and endpoints. The cdp-de repos are schemachange SQL migrations, Airflow DAGs and loaders: the unit is a Snowflake object and the edges are lineage, schedules and deployments.

Different questions

What feeds this table, and what breaks if it changes? Which DAG loads it, and when? Which source system is behind a data product? Will this SQL deploy, or will schemachange skip it?

Its own database

Database cdpde (GenAI: codekg locally, cdpgenai on the remote server). Neither uses the default neo4j database, which stays free for other apps. Each graph is rebuilt by its own pipeline with its own indexes.

The design decision that matters mostResolve names before linking anything. The SQL writes ${CEP_FIN_DB_NM}.${CDP_FIN_SCH_NM}.ACCOUNTING_DOCUMENT_TYPE; the extractor replays the shared deployment's variable substitution and uses the production name CEP_FIN_PROD.CDP_FIN.ACCOUNTING_DOCUMENT_TYPE as the id. One table is then one node in every repository that creates, reads or writes it, so lineage crosses data products. Names that can't be resolved keep their placeholder and say so (resolution: unresolved).

Step by step: the core ideas

  1. Resolve ${VARIABLES} to production names

    schemachange SQL names objects with placeholders. The shared deployment config of cdp-de-shared-workflows has their values per environment (a repository's config/<env>.yml can add its own). The extractor uses the prod value as the id, keeps the dev and qa values on ConfigKey, and marks how each name was found.

  2. Parse every statement: objects, columns and lineage

    Each script is split into statements (strings, quoted names and $$ bodies respected). CREATE statements become objects with their columns; the query of a view or dynamic table becomes DERIVED_FROM edges; INSERT, MERGE, UPDATE, COPY INTO and CALL in procedure bodies, DAG tasks and loaders become WRITES, READS and CALLS.

  3. Replay the deployment: will schemachange run the file?

    schemachange 4 runs only files under src/sql whose names match its patterns; anything else is skipped without an error. The renderer stops on a ${NAME} it has no value for, and pull requests are checked for names and headers. Each failed check becomes a code in File.deploy_issues (see the live tab).

  4. Read DAGs without running Airflow

    de_orch.py walks each DAG module with a small constant evaluator and the prod section of the JSON config the module loads, so DAG ids, schedules, SSH commands and f-string SQL come out as they run in production. Operators become DagTask nodes with a kind; >> chains become PRECEDES; a python_callable links to its Function, an SSH command to the loader File it runs, and calls of the ETL framework to EtlJob nodes.

  5. Derive lineage and roll-ups in Neo4j

    After loading, Cypher adds what no single file states: lineage through processes, what each DAG produces and consumes, the source systems behind each data product, and the counts the overview needs.

Keep it fresh: two clocks

Code clock every 30 minutes

  1. git ls-remote for every cdp-de repository's indexed branch (about 35 s when nothing moved).
  2. When any repository moved: save the summaries and embeddings, then rebuild the whole graph: c3 → c4 → reader grants → c9 → carry the enrichment over → c7 → c6.
  3. Only nodes whose input changed go back to the LLM (summary_hash, embed_hash).
  4. The database is recreated, so de answers fail for the minute or two of the load.

Status clock nightly

  1. Re-read GitHub metadata of the cdp-de repositories: workflows, runs, deployments, pull requests, teams, new or removed repositories.
  2. Then rebuild as above, so CI roll-ups and repository facts are at most a day old.
  3. Live CI questions go to github_live (GitHub MCP) instead.
Built: c8_refresh.py with CODEKG_DOMAIN=de, scheduled in Windows Task SchedulerTask codekg-refresh-de runs every 30 minutes (from 00:20, between the GenAI graph's runs) and codekg-refresh-de-nightly at 03:40. What the assistant does with this graph

The tools below are read live from the assistant's tool definitions (tools.tool_set("de")), with examples from its question library.

Lineage and impact: walking DERIVED_FROM

The lineage and impact_of_change tools walk the lineage breadth-first, one hop per query, so every object knows how far away it is and through which edge. Impact then adds the processes that read the affected objects, the DAGs that produce or consume them, and the data products whose repositories define them.

Guardrails specific to data engineering

Answer rules

  • Use object names exactly as the tools return them, in backticks: production names DB.SCHEMA.NAME.
  • Objects marked is_external / referenced only are used by the code but created by no indexed repository: say so.
  • Never present template copies (is_scaffold: sample DAGs, the WIDEN loader outside cdp-de-mrkt-widen, VAR_RESOLUTION_TEST objects) as a repository's own work.
  • Lineage through the control-table ETL framework is only partly visible in code (job and target, not the SQL): say so when it matters.
  • Schedules are cron expressions in the DAG's timezone (usually America/Los_Angeles): give them in words.

Shared with the GenAI assistant

  • Read-only Neo4j user codekg_reader (role codekg_read on cdpde) and a 25-second query timeout; text-to-Cypher runs EXPLAIN first and enforces a LIMIT.
  • Cite only URLs that appear in tool results: GitHub permalinks pinned to the indexed commit.
  • Every link and backticked name is checked against the tool outputs; anything unverified gets one repair turn and is then removed.
  • CI and deployment facts are "as of the last sync"; github_live facts are live.

Access checklist for phase 4

Snowflake

  • A service user with a read-only role: USAGE on the databases and schemas, REFERENCES (metadata, no data), and IMPORTED PRIVILEGES on the SNOWFLAKE database for ACCOUNT_USAGE.
  • SELECT on the ETL scripts control table only, to read job SQL.
  • Key-pair authentication, the key in a secret store.

Airflow (MWAA) and Neo4j

  • An IAM role that may call the Airflow REST API of the MWAA environment, used read-only: DAG runs and task instances.
  • A Neo4j Enterprise or Aura server for the remote graphs: databases cdpgenai and cdpde, never the default neo4j.
