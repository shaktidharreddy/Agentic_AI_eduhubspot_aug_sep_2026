Learning journey: how to learn and teach with this site

A suggested path through the modules: five short sittings to learn it yourself, then a ready-made plan for demonstrating and teaching it to beginners.

  • The grey Expected output boxes show what a correct run prints, so you can check your result.

Part 1 – Learn it yourself (5 sittings of 1–2 hours)

The method for every module

  1. Read the module text and look at its diagram.
  2. Type its Browser snippets by hand in Neo4j Browser (typing, not pasting, makes the syntax stick).
  3. Run its script and compare with the Expected output box.
  4. Answer the Checkpoint or "Try it yourself" questions where a module has them, before opening the solutions.
  5. Change one thing (a filter, a value, a question), predict the result, then run it.

2. The smallest possible connection script

This puts everything in one file so you can see the moving parts. Replace the password with yours.

from neo4j import GraphDatabase      # the official Neo4j driver (pip install neo4j)

URI = "neo4j://localhost:7687"       # Bolt address of your local database (port 7687)
AUTH = ("neo4j", "password123")      # <- your instance password

# "with" closes the driver automatically at the end of the block, even if an error happens.
with GraphDatabase.driver(URI, auth=AUTH) as driver:
    driver.verify_connectivity()     # raises an error if the DB is not reachable
    print("Connected!")

    # Write: create a node with properties
    # MERGE = create the Person only if one with this name doesn't exist yet.
    # $name and $role are parameters, filled from the dict on the next line.
    driver.execute_query(
        "MERGE (p:Person {name: $name}) SET p.role = $role",
        {"name": "Ada", "role": "analyst"},
        database_="neo4j",            # which database inside the server to use
    )

    # Read: query it back
    # execute_query returns (records, summary, keys): the rows, statistics, and column names.
    records, summary, keys = driver.execute_query(
        "MATCH (p:Person) RETURN p.name AS name, p.role AS role",
        database_="neo4j",
    )
    for record in records:
        # Access columns by the alias used after AS in the query.
        print(record["name"], "-", record["role"])
    print("Query took", summary.result_available_after, "ms")

    # Clean up the test node (DETACH DELETE also removes any relationships it has)
    driver.execute_query("MATCH (p:Person {name: 'Ada'}) DETACH DELETE p", database_="neo4j")
# Run the script with the active virtual environment's Python
python hello_neo4j.py
Connected!
Ada - analyst
Query took 2 ms

Create a .env file next to your script:

# Login details you set when creating the instance

import os

from dotenv import load_dotenv
from neo4j import GraphDatabase

load_dotenv()   # reads .env into environment variables

# Build the driver from settings in .env, so no password is written in the code.
driver = GraphDatabase.driver(
    os.getenv("NEO4J_URI"),
    auth=(os.getenv("NEO4J_USERNAME"), os.getenv("NEO4J_PASSWORD")),
)
driver.verify_connectivity()   # fail fast if the database is unreachable or the password is wrong

# datetime() is a built-in Cypher function returning the server's current time.
records, _, _ = driver.execute_query(
    "RETURN 'Hello from Neo4j' AS message, datetime() AS serverTime",
    database_=os.getenv("NEO4J_DATABASE", "neo4j"),
)
# records[0] is the first (and only) row; columns are read by their AS name.
print(records[0]["message"], "at", records[0]["serverTime"])
driver.close()   # release connections when done

4. Bonus: the session API (you'll see it in many tutorials)

execute_query is the simplest choice. Older examples use sessions and transactions, which do the same job:

from neo4j import GraphDatabase

with GraphDatabase.driver("neo4j://localhost:7687", auth=("neo4j", "password123")) as driver:
    # A session is a short-lived "conversation" with one database.
    with driver.session(database="neo4j") as session:
        # execute_read runs the function inside a READ transaction (and retries on temporary errors).
        # tx.run(...) sends the query; .single() takes the only row; ["c"] reads the column named c.
        count = session.execute_read(
            lambda tx: tx.run("MATCH (n) RETURN count(n) AS c").single()["c"]
        )
        print("Nodes in database:", count)

from neo4j import GraphDatabase

with GraphDatabase.driver("neo4j://localhost:7687", auth=("neo4j", "password123")) as driver:

    # IF NOT EXISTS = no error if it already exists; WAIT = return only when the new database is online.

Module 0

Welcome: a hands-on evidence knowledge graph

You'll build a small but real knowledge graph in your local Neo4j: clinical evidence (studies, results, documents) as a shared reference layer, and dossier work (claims, value messages, sections) as a project layer that links into that evidence instead of copying it.

What you'll be able to do by the end

  • Create nodes and relationships, both with properties, in Neo4j.
  • Query the graph with Cypher using patterns and value filters.
  • Add OpenAI embeddings to nodes and create a vector index.
  • Combine vector similarity search with normal Cypher filters (hybrid retrieval).
  • Write retrieval results back into the graph as project-scoped nodes (claims) that point to reference evidence.
  • Run cross-layer queries: traceability, reuse, impact analysis, gap finding.

The big idea in one picture

Reference layer

Entities that are true regardless of any dossier: Product, Indication, Study, Endpoint, Population, Result, SourceDocument.

Built once by ingestion and shared by every project. These nodes have no projectId.

Project layer

Entities that exist because a dossier project exists: Dossier, Section, ValueMessage, Claim.

Created by retrieval + authoring. Every one carries a projectId. A new GVD links into existing evidence instead of copying it.

1.4 The shared helper: kg.py

All scripts use these four helpers, which keeps each lesson focused on the Cypher.

"""Shared helpers used by every script in this course.

Every other script does `from kg import ...`, so connection details live in ONE place.
"""
import os                                   # read environment variables (our settings)

from dotenv import load_dotenv              # loads the key=value pairs from the .env file
from neo4j import GraphDatabase             # the official Neo4j Python driver

# Copy every line of .env into os.environ so os.getenv() can see it.
load_dotenv()

# --- Neo4j connection settings (second argument = default if .env does not set it) ---
NEO4J_URI = os.getenv("NEO4J_URI", "neo4j://localhost:7687")          # where the database listens
NEO4J_AUTH = (os.getenv("NEO4J_USERNAME", "neo4j"), os.getenv("NEO4J_PASSWORD"))  # (user, password)
NEO4J_DATABASE = os.getenv("NEO4J_DATABASE", "neo4j")                 # which database inside the server

# --- Embedding settings (used from Module 5 on) ---
EMBED_MODEL = "text-embedding-3-small"   # OpenAI model that turns text into numbers
EMBED_DIMS = 1536                        # how many numbers that model returns per text

# One driver object for the whole program. It manages a pool of connections for us,
# so we create it once here instead of connecting again for every query.
driver = GraphDatabase.driver(NEO4J_URI, auth=NEO4J_AUTH)


def run(cypher, **params):
    """Run one Cypher statement and return the rows as a list of plain dicts.

    Example:  run("MATCH (s:Study {id: $id}) RETURN s.name AS name", id="ZEN-301")
              -> [{'name': 'ZEN-301'}]
    Every keyword argument becomes a $parameter inside the Cypher text.
    """
    # execute_query sends the query, waits for all rows, and returns three things:
    # the records (rows), a summary (timings, counters) and the column names.
    records, _summary, _keys = driver.execute_query(cypher, params, database_=NEO4J_DATABASE)
    # record.data() converts each row into a normal Python dict: {column_name: value}.
    return [record.data() for record in records]


def show(rows, title=None):
    """Print query rows one per line, with an optional heading."""
    if title:
        print(f"\n== {title} ==")
    if not rows:                       # an empty list means the query matched nothing
        print("(no rows)")
    for row in rows:
        print(row)


def embed(texts):
    """Turn a list of strings into a list of embedding vectors (one list of 1536 floats per string)."""
    # Imported here (not at the top) so Modules 1-4 work even without an OpenAI key installed.
    from openai import OpenAI

    client = OpenAI()           # reads OPENAI_API_KEY (and optional OPENAI_BASE_URL) from the environment
    # One API call can embed many texts at once, which is faster and cheaper than one call per text.
    response = client.embeddings.create(model=EMBED_MODEL, input=texts)
    # response.data has one item per input text, in the same order; .embedding is the vector.
    return [item.embedding for item in response.data]

Graph concepts & our minimal schema

A knowledge graph stores data as nodes (things) and relationships (how things connect). Both can hold properties.

2.1 The four building blocks

NodeA data record for one thingthe study ZEN-301

PropertyA key-value pair stored on a node or a relationshipphase: 3, page: 45
RelationshipA directed, typed link between two nodes, which can also hold properties(Study)-[:REPORTS {primary:true}]->(Result)

Cypher draws graphs with ASCII art: nodes in (), relationships in [], direction with ->.

// A node:  (variable:Label {property: value})
// A relationship:  -[:TYPE {property: value}]->   (the arrow shows the direction)

Build the reference graph (ingestion)

3.1 Hands-on in Neo4j Browser

Create a node with properties

MERGE means "find it, or create it if it doesn't exist", so running it twice never makes a duplicate. SET writes properties.

// MERGE: find a Product with this id, or create it if none exists (never duplicates)
MERGE (p:Product {id: 'P-ZEN'})
// SET: write (or overwrite) properties on the node
SET p.name = 'Zentrax', p.type = 'investigational'
// RETURN: show the node in the result panel
RETURN p
// Same pattern for a Study: numbers are stored as numbers, text in quotes
MERGE (s:Study {id: 'ZEN-301'})
SET s.name = 'ZEN-301', s.phase = 3, s.design = 'RCT vs placebo', s.year = 2024, s.n = 600
RETURN s

Create a relationship with properties

To connect two nodes, MATCH them first, then MERGE the relationship between them.

// 1) MATCH finds the two existing nodes (comma = both patterns at once)
MATCH (s:Study {id: 'ZEN-301'}), (p:Product {id: 'P-ZEN'})
// 2) MERGE creates the arrow Study -> Product only if it is not there yet
MERGE (s)-[e:EVALUATES]->(p)
// 3) relationships can have properties too
SET e.role = 'investigational arm'
RETURN s, e, p

Read it back

// Find every Study that EVALUATES a Product and return one row per match
MATCH (s:Study)-[e:EVALUATES]->(p:Product)
RETURN s.name AS study, e.role AS role, p.name AS product

3.2 Uniqueness constraints

A constraint guarantees that no two nodes with the same label share an id. It also creates an index, which makes MERGE and MATCH by id fast. The script creates one per label, like this:

// No two Study nodes may have the same id. Also creates an index, so lookups by id are fast.
// IF NOT EXISTS: safe to run again
CREATE CONSTRAINT study_id IF NOT EXISTS
FOR (n:Study) REQUIRE n.id IS UNIQUE

        run(f"CREATE CONSTRAINT {label.lower()}_id IF NOT EXISTS FOR (n:{label}) REQUIRE n.id IS UNIQUE")


def load_nodes():
    """Create (or update) every node with a single query per label."""
    # Labels cannot be parameters in Cypher, so the label goes in the f-string; values stay as $parameters.
    # {{ and }} are how you write a literal { } inside a Python f-string.
    for label, rows in NODES.items():

        # MERGE finds the node with that id, or creates it if missing (so no duplicates on re-run).
        # SET n += row copies every key of the dict onto the node as properties.
        run(f"UNWIND $rows AS row MERGE (n:{label} {{id: row.id}}) SET n += row", rows=rows)

            MERGE (a)-[r:{rel_type}]->(b)
            // 3) copy the property dict onto the relationship
            SET r += $props
        """, fid=from_id, tid=to_id, props=props)

Query with Cypher: patterns and value filters

Cypher works by pattern matching: you describe the shape you want and Neo4j finds every place in the graph that fits. No vectors yet, just exact filters.

4.1 Single-node patterns

// labels(n) is a list like ['Study']; [0] takes the first label
// count(*) counts rows per label (Cypher groups by the non-aggregated columns automatically)
MATCH (n)
RETURN labels(n)[0] AS label, count(*) AS count
ORDER BY label
// Return only the properties you need instead of whole nodes
MATCH (s:Study)
RETURN s.id, s.design, s.year, s.n
ORDER BY s.year

// count() and collect() are aggregations: one output row per endpoint

// Start from every product...
MATCH (p:Product)

4.4 Variable-length paths

*1.. means "follow this relationship type one or more times". It's handy for hierarchies like population subgroups.

// *1.. = follow SUBGROUP_OF one or more times (handles subgroups of subgroups too)
// path = the whole matched chain; length(path) = number of relationships in it
MATCH path = (sub:Population)-[:SUBGROUP_OF*1..]->(parent:Population)
RETURN sub.name AS subgroup, parent.name AS parent, length(path) AS hops
// [*1..2] = any relationship type, 1 or 2 hops; no arrow head = either direction
MATCH path = (s:Study {id: 'ZEN-302'})-[*1..2]-(x)
RETURN path

Module 5 · Reference layer

Add OpenAI embeddings and a vector index

Exact filters need exact words. To find "results about skin clearance" when the text says "PASI 75", we need semantic search. We turn each Result.text into a vector and index it.

5.1 What's happening

  1. Read every Result that doesn't have an embedding yet.
  2. Send its text to OpenAI text-embedding-3-small, which returns 1536 numbers.
  3. Store the list on the node as the property embedding.
  4. Create a vector index on Result.embedding with cosine similarity.
Why embed Result and not everything?In this schema, results are what the retrieval step looks for. Studies, endpoints and documents are reached by following relationships from a matched result. That's the graph advantage over plain vector RAG.

5.2 The script

"""Module 5 – add OpenAI embeddings to Result nodes and create a vector index.

An embedding is a list of numbers that captures the MEANING of a text.
Texts with similar meaning get vectors that point in similar directions,
which is what makes "semantic" search possible.
"""
from kg import EMBED_DIMS, embed, run, show

# 1. Which results still need an embedding? Re-running the script only embeds new ones,
#    so you never pay OpenAI twice for the same text.
todo = run("MATCH (r:Result) WHERE r.embedding IS NULL RETURN r.id AS id, r.text AS text")
print(f"{len(todo)} result(s) to embed")

if todo:
    # 2. One API call for the whole batch: send all texts, get back one vector per text (same order).
    vectors = embed([row["text"] for row in todo])

    # 3. Store each vector as a list property called "embedding" on its node.
    #    zip() pairs each row with its vector; we send them all in one query via UNWIND.
    run("""
        UNWIND $rows AS row

Module 6 · Reference layer

Vector search + normal property filters (hybrid retrieval)

Use the vector index to find semantically similar results, then use ordinary Cypher patterns and WHERE filters to narrow them down and pull in connected context.

6.1 The SEARCH clause

Since Neo4j 2026.01, vector search is part of MATCH itself: you write a normal node pattern and add a SEARCH subclause that lets the vector index choose which nodes match.

CYPHER 25                       // use the Cypher version that has SEARCH (safe even if it is already the default)
MATCH (r:Result)                // r = the nodes we want to find
  SEARCH r IN (
    VECTOR INDEX result_embedding   // which vector index to ask (name, not in quotes)
    FOR $questionVector             // the question's embedding (a list of 1536 numbers)
    LIMIT $k                        // how many nearest neighbours to return
  ) SCORE AS score              // similarity in [0, 1], higher = closer
RETURN r.id, score
ORDER BY score DESC
Older Neo4j (before 2026.01)?Use the older procedure, which gives the same nodes and scores:
CALL db.index.vector.queryNodes('result_embedding', $k, $questionVector) YIELD node AS r, score
Neo4j 2026.x still runs it but shows a deprecation warning.

Try it in Browser without an API call: "more like this"

You can use an existing node's embedding as the query vector:

// Use an existing node's embedding as the "question": find results similar to R4
CYPHER 25
MATCH (seed:Result {id: 'R4'})
// SEARCH must be in its own MATCH, and its pattern may contain only the searched node
MATCH (node:Result)
  SEARCH node IN (VECTOR INDEX result_embedding FOR seed.embedding LIMIT 4) SCORE AS score
WITH node, score
WHERE node <> seed                 // the most similar node is R4 itself, so skip it
RETURN node.id, round(score, 3) AS score, node.text

You'll most likely see R5 and R1 near the top, since they're also PASI 75 results.

6.2 Pure vector vs. vector + filters

The key pattern is: vector search first → MATCH the surrounding graph → filter with WHERE.

CYPHER 25
// 1) the vector index proposes the k most similar results (as r) with their score
MATCH (r:Result)
  SEARCH r IN (VECTOR INDEX result_embedding FOR $qvec LIMIT $k) SCORE AS score
// 2) walk from each candidate to its study, endpoint, comparator and population
MATCH (s:Study)-[:REPORTS]->(r)-[:MEASURES]->(e:Endpoint),
      (r)-[:VERSUS]->(cmp:Product),
      (r)-[:FOR_POPULATION]->(pop:Population)
// 3) keep only candidates that pass the filters
WHERE score >= $minScore
  AND ($category IS NULL OR e.category = $category)      // optional filter
  AND ($versus   IS NULL OR cmp.name   = $versus)        // optional filter
  AND ($maxP     IS NULL OR r.pValue  <= $maxP)          // optional filter
  AND NOT EXISTS { (:Result)-[:SUPERSEDES]->(r) }        // skip outdated results (Module 8)
RETURN r.id AS id, round(score, 3) AS score, s.id AS study, e.name AS endpoint,
       cmp.name AS versus, pop.name AS population, r.text AS text
ORDER BY score DESC
The $x IS NULL OR ... trickThis lets one fixed query serve every combination of filters. Pass None to switch a filter off. You avoid building Cypher strings by hand, so there's no injection risk.
Post-filtering caveatSEARCH returns the top k before your WHERE runs. If filters remove most hits, you can end up with too few rows. Ask for a larger k (for example 10–50) than the number of rows you finally want.

6.3 The retrieval module

"""Module 6 – vector search, hybrid (vector + filter) search, and graph-expanded context.

Three ideas, from simple to powerful:
  plain_search()  – "which results MEAN something similar to my question?"
  search()        – the same, plus exact filters on the graph (category, comparator, p-value)
  context_for()   – follow relationships from the hits to their study and source page
"""
import os

from kg import embed, run, show

# The SEARCH clause (Neo4j 2026.01+, Cypher 25) asks the vector index 'result_embedding'
# for the k Result nodes whose embeddings are closest to the query vector ($qvec).
# SCORE AS score adds the similarity (0..1, higher = closer).
# "CYPHER 25" on the first line makes sure the new syntax is used even if the database
# defaults to the older Cypher 5.
PLAIN_SEARCH = """
CYPHER 25
MATCH (r:Result)
  SEARCH r IN (VECTOR INDEX result_embedding FOR $qvec LIMIT $k) SCORE AS score
RETURN r.id AS id, round(score, 3) AS score, r.text AS text
ORDER BY score DESC
"""

# Hybrid search = vector search first, then ordinary Cypher on the hits:
#   1. SEARCH lets the vector index propose the k most similar Result nodes (named r)
#   2. the second MATCH walks from r to its study, endpoint, comparator and population
#   3. WHERE keeps only the rows that pass the filters
# "$category IS NULL OR ..." means: if Python passed None, the filter is switched off.
HYBRID_SEARCH = """
CYPHER 25
MATCH (r:Result)
  SEARCH r IN (VECTOR INDEX result_embedding FOR $qvec LIMIT $k) SCORE AS score
MATCH (s:Study)-[:REPORTS]->(r)-[:MEASURES]->(e:Endpoint),
      (r)-[:VERSUS]->(cmp:Product),
      (r)-[:FOR_POPULATION]->(pop:Population)
WHERE score >= $minScore
  AND ($category IS NULL OR e.category = $category)
  AND ($versus   IS NULL OR cmp.name   = $versus)
  AND ($maxP     IS NULL OR r.pValue  <= $maxP)
  AND NOT EXISTS { (:Result)-[:SUPERSEDES]->(r) }   // skip results replaced by a newer one (Module 8)
RETURN r.id AS id, round(score, 3) AS score, s.id AS study, e.name AS endpoint,
       cmp.name AS versus, pop.name AS population, r.text AS text
ORDER BY score DESC
"""

# Graph expansion: given result ids, collect the extra facts an LLM needs to cite properly.
CONTEXT = """
MATCH (s:Study)-[:REPORTS]->(r:Result)-[x:EXTRACTED_FROM]->(d:SourceDocument)
WHERE r.id IN $ids
RETURN r.id AS id, r.text AS text, s.id AS study, s.design AS design, s.n AS n,
       d.title AS source, x.page AS page
"""


def plain_search(question, k=3):
    """Vector similarity only."""
    # embed() takes a LIST of texts and returns a list of vectors; [0] picks the one vector we need.
    return run(PLAIN_SEARCH, k=k, qvec=embed([question])[0])


def search(question, k=10, min_score=0.0, category=None, versus=None, max_p=None):
    """Vector similarity + optional graph/value filters. Pass None to switch a filter off.

    k         – how many candidates the vector index returns BEFORE filtering (keep it generous)
    min_score – drop weak matches (0.7 is a sensible start for this model)
    """
    return run(HYBRID_SEARCH, k=k, qvec=embed([question])[0], minScore=min_score,
               category=category, versus=versus, maxP=max_p)


def context_for(result_ids):
    """Follow relationships from matched results to their study and source page."""
    return run(CONTEXT, ids=result_ids)


def answer(question, search_fn=search):
    """Optional bonus: GraphRAG – retrieve, expand via the graph, then ask an LLM.
    search_fn lets Module 6P swap in pgvector retrieval without changing this function."""
    from openai import OpenAI

    # Step 1 – RETRIEVE: best 3 results above the threshold.
    hits = search_fn(question, k=5, min_score=0.7)[:3]
    # Step 2 – EXPAND: fetch study design, sample size and page for each hit, and format
    #          them as bullet lines the LLM can quote.
    evidence = "\n".join(
        f"- {c['text']} (Study {c['study']}, {c['design']}, n={c['n']}; source: {c['source']}, p.{c['page']})"
        for c in context_for([h["id"] for h in hits])
    )
    # Step 3 – GENERATE: the system message restricts the model to our evidence (reduces hallucination).
    response = OpenAI().chat.completions.create(
        model=os.getenv("OPENAI_CHAT_MODEL", "gpt-4o-mini"),
        messages=[
            {"role": "system", "content": "Answer only from the evidence and cite the source and page. "
                                          "If the evidence is insufficient, say you don't know."},
            {"role": "user", "content": f"Evidence:\n{evidence}\n\nQuestion: {question}"},
        ],
    )
    return response.choices[0].message.content

Module 7 · Project layer

Retrieval writes project nodes into the graph

This is where the two layers meet. A dossier project defines sections and value messages. For each claim we retrieve evidence with hybrid search and write a Claim node whose BASED_ON relationships point at the shared reference Result nodes. Nothing is copied.

7.1 The flow

  1. Project skeleton: create Dossier → Sections and ValueMessages, all stamped with projectId.
  2. Retrieve: run search() from Module 6 with a question and filters.
  3. Ingest the retrieval: MERGE a Claim (with projectId), connect it to its section and value message, and create BASED_ON relationships to the hits. The retrieval score and query are stored on the relationship for auditability.
Project-layer rules
  • Every project node has projectId.
  • Project ids are prefixed, for example GVD-DE-2026:C1, so they're unique across projects.
  • A claim can only attach to a section or value message of the same project (enforced in the MATCH).
Why store score and query on BASED_ON?A reviewer can later ask "why is this result linked to this claim?" and see the search question and score that produced the link.

7.2 The script

"""Module 7 – PROJECT layer: dossier skeleton + claims written from retrieval results.
Every node created here carries a projectId and links INTO the reference layer.

Flow:  create_project()  ->  write_claim() = search() + WRITE_CLAIM query
"""
from kg import run, show
from s4_vector_search import search          # the hybrid search from Module 6

PROJECT_LABELS = ["Dossier", "Section", "ValueMessage", "Claim"]


def ensure_project_schema():
    """Constraints + indexes for the project-layer labels (safe to run every time)."""
    for label in PROJECT_LABELS:
        # Unique ids, exactly like the reference layer.
        run(f"CREATE CONSTRAINT {label.lower()}_id IF NOT EXISTS FOR (n:{label}) REQUIRE n.id IS UNIQUE")
        # An ordinary index on projectId makes "give me everything of project X" fast.
        run(f"CREATE INDEX {label.lower()}_project IF NOT EXISTS FOR (n:{label}) ON (n.projectId)")


def create_project(pid, name, market, sections, value_messages):
    """Create the dossier, its sections and its value messages. All get projectId = pid."""
    run("""
        // the dossier node itself; its id IS the project id
        MERGE (d:Dossier {id: $pid})
        SET d.projectId = $pid, d.name = $name, d.market = $market
        // WITH passes d on to the next part of the query
        WITH d
        // one row per section dict in the $sections list
        UNWIND $sections AS sec
        // ids are prefixed with the project id ('GVD-DE-2026:S-EFF') so they are unique across projects
        MERGE (s:Section {id: $pid + ':' + sec.key})
        SET s.projectId = $pid, s.title = sec.title, s.order = sec.order
        MERGE (s)-[:PART_OF]->(d)
    """, pid=pid, name=name, market=market, sections=sections)

    run("""
        UNWIND $vms AS vm
        MERGE (v:ValueMessage {id: $pid + ':' + vm.key})
        SET v.projectId = $pid, v.text = vm.text
    """, pid=pid, vms=value_messages)


# Writes ONE claim plus all its links in a single query.
WRITE_CLAIM = """
// 1) Find the value message and section. Requiring projectId = $pid means a claim
//    can never be attached to another project's section by mistake.
MATCH (vm:ValueMessage {id: $vmId, projectId: $pid}),
      (sec:Section     {id: $secId, projectId: $pid})
// 2) Create/update the claim node (project layer, so it gets projectId).
MERGE (c:Claim {id: $claimId})
SET c.projectId = $pid, c.text = $text, c.status = 'draft', c.updatedAt = datetime()
// 3) Project-layer links.
MERGE (c)-[:SUPPORTS]->(vm)
MERGE (c)-[a:APPEARS_IN]->(sec)
SET a.order = $order
// 4) The BRIDGE into the reference layer: one BASED_ON per retrieved result.
//    The retrieval score, method and question are stored ON the relationship for auditing.
WITH c
UNWIND $evidence AS ev
MATCH (r:Result {id: ev.id})
MERGE (c)-[b:BASED_ON]->(r)
SET b.score = ev.score, b.method = $method, b.query = $question, b.linkedAt = datetime()
RETURN c.id AS claim, collect(r.id) AS basedOn
"""


def write_claim(pid, key, text, vm_key, section_key, question,
                order=1, top_n=2, min_score=0.7, search_fn=search, method="neo4j-vector+filter", **filters):
    """Retrieve evidence for a claim, then write the claim and its BASED_ON links.
    search_fn / method let Module 7P plug in pgvector retrieval instead of the Neo4j vector index.

    pid / key        – project id and short claim key; the stored id becomes 'pid:key'
    question         – what we search for in the evidence
    top_n            – how many of the best hits become BASED_ON links
    **filters        – any extra keyword (category=..., versus=...) is passed on to the search
    """
    # RETRIEVAL: ask for 10 candidates, keep the best top_n.
    hits = search_fn(question, k=10, min_score=min_score, **filters)[:top_n]
    if not hits:
        # No good evidence: better to write nothing than an unsupported claim.
        print(f"No evidence above {min_score} for {question!r}; claim NOT written")
        return []
    print(f"\n{pid}:{key}  retrieved -> {[(h['id'], h['score']) for h in hits]}")
    # INGESTION: write the claim and its links back into the graph.
    rows = run(WRITE_CLAIM, pid=pid, claimId=f"{pid}:{key}", text=text,
               vmId=f"{pid}:{vm_key}", secId=f"{pid}:{section_key}", order=order,
               question=question, method=method,
               evidence=[{"id": h["id"], "score": h["score"]} for h in hits])
    if not rows:
        # The MATCH in step 1 found nothing (wrong key or another project's section).
        print("Section or value message not found in this project; nothing written")
    return rows

Module 8 · Both layers

Cross-layer capability queries

The schema was designed backwards from questions like these. Each one is a short Cypher pattern because the answer is literally a path in the graph.

CapabilityQuestionPattern
TraceabilityWhere exactly does this claim come from?Claim → Result → SourceDocument (page)
ReuseWhich evidence is used by more than one dossier?Result ← Claim, grouped by projectId
Gap findingWhich value messages have no supporting claim?ValueMessage without an incoming SUPPORTS
Impact analysisA result was updated. Which claims in which dossiers must be reviewed?new SUPERSEDES old ← Claim → Section → Dossier

8.1 The script

"""Module 8 – capability queries that cross the reference and project layers.

Each question below is answered by ONE graph pattern, because the answer is literally a path:
  1. Traceability  Claim -> Result -> SourceDocument (page)
  2. Reuse         Result <- Claims from several projects
  3. Gaps          ValueMessage with no incoming SUPPORTS
  4. Impact        new Result SUPERSEDES old Result <- Claim -> Section -> Dossier
  5. Isolation     delete one project without touching shared evidence
"""
from kg import embed, run, show
from s5_project_layer import create_project

#    Two MATCH clauses: the first walks claim -> result -> document, the second adds the study.
show(run("""
    MATCH (c:Claim {id: $claimId})-[b:BASED_ON]->(r:Result)-[x:EXTRACTED_FROM]->(d:SourceDocument)
    MATCH (s:Study)-[:REPORTS]->(r)
    RETURN r.id AS result, b.score AS score, s.id AS study, d.title AS document, x.page AS page, x.table AS tbl
    ORDER BY result

5P.4 The Postgres helper: pg.py

This is the counterpart of kg.py. register_vector lets you pass and receive vectors as Python objects, and search_path makes our schema plus public (where pgvector usually lives) visible.

"""pgvector helpers – the Postgres counterpart of kg.py."""
import os

import psycopg                                     # PostgreSQL driver for Python (version 3)
from dotenv import load_dotenv
from pgvector.psycopg import register_vector       # teaches psycopg the 'vector' column type

load_dotenv()

PG_SCHEMA = os.getenv("PG_SCHEMA", "kg_gvd")   # our own schema keeps the course isolated
TABLE = f"{PG_SCHEMA}.result_embeddings"        # fully qualified table name: schema.table


def pg_connect(register=True):
    """Open an autocommit connection. register=True teaches psycopg the 'vector' type.

    Use it with `with pg_connect() as conn:` so the connection is closed automatically.
    """
    conn = psycopg.connect(
        host=os.getenv("PG_HOST", "localhost"),
        port=int(os.getenv("PG_PORT", "5432")),
        dbname=os.getenv("PG_DBNAME", "postgres"),
        user=os.getenv("PG_USER", "postgres"),
        password=os.getenv("PG_PASSWORD"),
        # search_path = where Postgres looks for unqualified names (tables, types, functions).
        options=f"-c search_path={PG_SCHEMA},public",   # pgvector is usually installed in 'public'
        # autocommit: every statement is saved immediately (no explicit COMMIT needed).
        autocommit=True,
    )
    if register:
        # Needs the extension to exist already; that's why setup connects once with register=False.
        register_vector(conn)
    return conn


def pg_rows(conn, sql, params=None):
    """Run a SELECT and return a list of dicts (same shape as kg.run)."""
    cur = conn.execute(sql, params)                    # params fills the %(name)s placeholders
    cols = [c.name for c in cur.description]           # column names of the result
    return [dict(zip(cols, row)) for row in cur.fetchall()]   # turn each tuple into {column: value}

5P.6 Sync the graph into pgvector

Unlike Module 5, this is a sync. It reads results from Neo4j, embeds only new or changed texts, refreshes the copied filter columns, and deletes rows whose Result no longer exists. Re-running it is safe and cheap.

"""Module 5P – store Result embeddings in pgvector instead of on the graph nodes.
Neo4j stays the source of truth; Postgres holds one row per Result, keyed by Result.id."""
from pgvector import Vector                        # wraps a Python list so it is sent as a pgvector value

from kg import EMBED_DIMS, EMBED_MODEL, embed, run, show
from pg import PG_SCHEMA, TABLE, pg_connect, pg_rows

# SQL run once (all statements use IF NOT EXISTS, so re-running is harmless).
SETUP_SQL = [
    # enable pgvector in this database (adds the 'vector' type and the <=> distance operator)
    "CREATE EXTENSION IF NOT EXISTS vector",
    # a separate schema = a separate "folder" for our tables, isolated from other apps
    f"CREATE SCHEMA IF NOT EXISTS {PG_SCHEMA}",
    f"""CREATE TABLE IF NOT EXISTS {TABLE} (
            result_id         text PRIMARY KEY,          -- = Result.id in Neo4j (the join key)
            content           text NOT NULL,             -- the exact text that was embedded
            model             text NOT NULL,             -- which embedding model produced the vector
            study_id          text,                      -- filter columns copied from the graph
            endpoint_category text,
            versus            text,
            p_value           double precision,
            embedding         vector({EMBED_DIMS}) NOT NULL,
            updated_at        timestamptz NOT NULL DEFAULT now()
        )""",
    # HNSW = an approximate-nearest-neighbour index; vector_cosine_ops = rank by cosine distance
    f"""CREATE INDEX IF NOT EXISTS result_embeddings_hnsw
        ON {TABLE} USING hnsw (embedding vector_cosine_ops)""",
]

# Read every Result plus the facts we copy into the filter columns.
GRAPH_RESULTS = """
MATCH (s:Study)-[:REPORTS]->(r:Result)-[:MEASURES]->(e:Endpoint),
      (r)-[:VERSUS]->(cmp:Product)
RETURN r.id AS id, r.text AS text, s.id AS study, e.category AS category,
       cmp.name AS versus, r.pValue AS p
ORDER BY id
"""

# "Upsert" = INSERT a new row, or UPDATE it if the primary key already exists.
# %(name)s are psycopg placeholders, filled from a dict with the same keys.
UPSERT = f"""
INSERT INTO {TABLE} (result_id, content, model, study_id, endpoint_category, versus, p_value, embedding)
VALUES (%(id)s, %(text)s, %(model)s, %(study)s, %(category)s, %(versus)s, %(p)s, %(embedding)s)
ON CONFLICT (result_id) DO UPDATE SET
    content = EXCLUDED.content, model = EXCLUDED.model, study_id = EXCLUDED.study_id,
    endpoint_category = EXCLUDED.endpoint_category, versus = EXCLUDED.versus,
    p_value = EXCLUDED.p_value, embedding = EXCLUDED.embedding, updated_at = now()
"""

# Cheap update of the copied columns only (no new embedding needed).
REFRESH_METADATA = f"""
UPDATE {TABLE}
SET study_id = %(study)s, endpoint_category = %(category)s, versus = %(versus)s, p_value = %(p)s
WHERE result_id = %(id)s
"""


def setup(conn):
    """Create extension, schema, table and index if they don't exist yet."""
    for statement in SETUP_SQL:
        conn.execute(statement)


def sync():
    """Make the pgvector table match the graph: embed new/changed results, refresh filters, drop orphans."""
    graph_rows = run(GRAPH_RESULTS)                 # what the graph says (source of truth)
    with pg_connect(register=False) as conn:
        setup(conn)                                # the extension must exist before register_vector()
    with pg_connect() as conn:
        # What Postgres already has: {result_id: content}
        stored = {r["result_id"]: r["content"] for r in pg_rows(conn, f"SELECT result_id, content FROM {TABLE}")}

        # 1. embed only results that are new or whose text changed
        #    (stored.get() returns None for ids that are not in Postgres yet)
        todo = [r for r in graph_rows if stored.get(r["id"]) != r["text"]]
        if todo:
            vectors = embed([r["text"] for r in todo])
            with conn.cursor() as cur:
                # executemany runs the same SQL once per dict; {**r, ...} copies r and adds two keys.
                cur.executemany(UPSERT, [{**r, "model": EMBED_MODEL, "embedding": Vector(v)}
                                         for r, v in zip(todo, vectors)])

        # 2. refresh the copied filter columns for everything else (cheap, no API call)
        unchanged = [r for r in graph_rows if r not in todo]
        if unchanged:
            with conn.cursor() as cur:
                cur.executemany(REFRESH_METADATA, unchanged)

        # 3. remove rows whose Result no longer exists in the graph
        #    set(stored) = ids in Postgres; minus the ids in the graph = leftovers ("orphans")
        orphans = sorted(set(stored) - {r["id"] for r in graph_rows})
        if orphans:
            # ANY(%s) matches any value of a Python list passed as one parameter
            conn.execute(f"DELETE FROM {TABLE} WHERE result_id = ANY(%s)", (orphans,))

        print(f"embedded {len(todo)}, refreshed {len(unchanged)}, deleted orphans {orphans}")
        # vector_dims() is a pgvector function returning the length of a vector.
        return pg_rows(conn, f"""
            SELECT result_id, endpoint_category, versus, vector_dims(embedding) AS dims, model
            FROM {TABLE} ORDER BY result_id
        """)


if __name__ == "__main__":
    show(sync(), f"Rows in {TABLE}")

Module 6P · pgvector track (counterpart of Module 6)

pgvector search + SQL filters + Cypher filters

Retrieval now runs in two steps. pgvector finds the nearest results, optionally filtered in SQL. Then Neo4j applies graph filters and adds context. The function returns exactly the same shape as Module 6's search(), so everything downstream works unchanged.

6P.1 Vector search in SQL

pgvector adds distance operators. <=> is cosine distance, so cosine similarity is 1 - distance. ORDER BY embedding <=> :q LIMIT k is the query shape that uses the HNSW index.

-- <=> = cosine DISTANCE (0 = identical direction); 1 - distance = cosine similarity
-- $1 = the question's embedding, passed in by the program
SELECT result_id, 1 - (embedding <=> $1) AS cosine
FROM kg_gvd.result_embeddings
WHERE endpoint_category = 'safety'          -- optional SQL filter
ORDER BY embedding <=> $1                  -- nearest first (uses the HNSW index)
LIMIT 10;

Try it in SQL without an API call: "more like this"

-- Self-join: a = the seed row (R4), b = every other row; rank b by distance to a
SELECT b.result_id, round((1 - (b.embedding <=> a.embedding))::numeric, 3) AS cosine
FROM kg_gvd.result_embeddings a
JOIN kg_gvd.result_embeddings b ON b.result_id <> a.result_id
WHERE a.result_id = 'R4'
ORDER BY b.embedding <=> a.embedding
LIMIT 3;

6P.2 Two places to filter

In SQL (before the vector ranking)Uses the columns copied into the table: endpoint_category, versus, p_value. Fast and simple, but it only knows what you copied.
In Cypher (after the vector ranking)Pass the hits as $hits, UNWIND them, MATCH the graph and filter on anything: population, superseded status, study design, and more.
Same scores as Module 6Neo4j reports cosine as (1 + cosine) / 2. We convert pgvector's cosine to that scale, so the min_score=0.7 threshold means the same thing in both tracks. In our test run, the safety query scored R3 = 0.675 and R6 = 0.649 in both stores.

"""Module 6P – vector search in pgvector, filters in SQL and/or Cypher, context from the graph."""
from pgvector import Vector

from kg import embed, run, show

# <=> is pgvector's COSINE DISTANCE operator (0 = same direction, 2 = opposite).
# Cosine similarity = 1 - distance. ORDER BY ... <=> ... LIMIT k is the pattern the HNSW index speeds up.
PLAIN_SQL = f"""
SELECT result_id AS id,
       round((1 - (embedding <=> %(q)s))::numeric, 3)::float8 AS cosine,
       content AS text
FROM {TABLE}
ORDER BY embedding <=> %(q)s
LIMIT %(k)s
"""

# Same query plus optional SQL filters on the copied columns.
# "%(category)s::text IS NULL OR ..." switches a filter off when Python passes None;
# the ::text / ::float8 casts tell Postgres the type of a NULL parameter.
FILTERED_SQL = f"""
SELECT result_id AS id, 1 - (embedding <=> %(q)s) AS cosine
FROM {TABLE}
WHERE (%(category)s::text IS NULL OR endpoint_category = %(category)s)
  AND (%(versus)s::text   IS NULL OR versus = %(versus)s)
  AND (%(max_p)s::float8  IS NULL OR p_value <= %(max_p)s)
ORDER BY embedding <=> %(q)s
LIMIT %(k)s
"""

# Step 2 runs in Neo4j: the pgvector hits arrive as a list of {id, score} dicts.
# UNWIND turns the list into rows, MATCH finds each Result and its neighbours,
# WHERE applies filters that only the graph can answer (population, superseded).
GRAPH_FILTER = """
UNWIND $hits AS hit
MATCH (s:Study)-[:REPORTS]->(r:Result {id: hit.id})-[:MEASURES]->(e:Endpoint),
      (r)-[:VERSUS]->(cmp:Product),
      (r)-[:FOR_POPULATION]->(pop:Population)
WHERE hit.score >= $minScore
  AND ($population IS NULL OR pop.name = $population)
  AND NOT EXISTS { (:Result)-[:SUPERSEDES]->(r) }
RETURN r.id AS id, hit.score AS score, s.id AS study, e.name AS endpoint,
       cmp.name AS versus, pop.name AS population, r.text AS text
ORDER BY score DESC
"""


def plain_search_pg(question, k=3):
    """pgvector only: nearest rows by cosine distance."""
    with pg_connect() as conn:
        # Vector(...) wraps the Python list so psycopg sends it as a pgvector value.
        return pg_rows(conn, PLAIN_SQL, {"q": Vector(embed([question])[0]), "k": k})


def search_pg(question, k=10, min_score=0.0, category=None, versus=None, max_p=None, population=None):
    """Same signature and output as s4_vector_search.search(), but the vectors live in Postgres.
    1) pgvector: similarity + SQL filters on copied columns  2) Neo4j: graph filters + context."""
    # Step 1 – Postgres: nearest results that pass the SQL filters.
    with pg_connect() as conn:
        hits = pg_rows(conn, FILTERED_SQL, {"q": Vector(embed([question])[0]), "k": k,
                                            "category": category, "versus": versus, "max_p": max_p})
    # Convert cosine (-1..1) to Neo4j's score scale (0..1) so thresholds mean the same in both tracks.
    hits = [{"id": h["id"], "score": round((1 + float(h["cosine"])) / 2, 3)} for h in hits]
    # Step 2 – Neo4j: graph filters + the same output columns as Module 6.
    return run(GRAPH_FILTER, hits=hits, minScore=min_score, population=population)

Module 8P · pgvector track (counterpart of Module 8)

Capability queries with two stores: keep them in sync

Traceability, reuse and gap queries are pure graph queries, so they work exactly as in Module 8. What's new with an external vector store is consistency. When ingestion changes the graph, pgvector has to follow.

8P.1 The update scenario

  1. Ingestion adds a final analysis R4-FINAL to the graph and marks it SUPERSEDES R4. pgvector doesn't know about it yet.
  2. A consistency report shows missing_in_pgvector: ['R4-FINAL'].
  3. sync() from Module 5P embeds it, and the report is clean again.
  4. Retrieval now returns R4-FINAL. The old R4 row is still in pgvector, but the graph filter hides it.
  5. The impact query flags every claim in any project, from either track that relied on R4.
Why keep R4 in pgvector?Superseded is a graph fact. Keeping that rule in one place (Cypher NOT EXISTS { (:Result)-[:SUPERSEDES]->(r) }) means you never have to copy it into SQL. The sync only deletes rows whose node is actually gone.

8P.2 The script

"""Module 8P – capability queries when vectors live in pgvector: keeping two stores in sync."""
from kg import run, show
from pg import TABLE, pg_connect, pg_rows
from s3p_embed_pg import sync
from s4p_vector_search_pg import search_pg


def consistency_report():
    """Compare the set of Result ids in Neo4j with the set of ids in pgvector."""
    graph_ids = {r["id"] for r in run("MATCH (r:Result) RETURN r.id AS id")}      # {...} = a Python set
    with pg_connect() as conn:
        pg_ids = {r["result_id"] for r in pg_rows(conn, f"SELECT result_id FROM {TABLE}")}
    # Set difference (a - b) = items in a that are not in b.
    return [{"in_graph": len(graph_ids), "in_pgvector": len(pg_ids),
             "missing_in_pgvector": sorted(graph_ids - pg_ids), "orphans_in_pgvector": sorted(pg_ids - graph_ids)}]


# 1. Ingestion adds a corrected result to the GRAPH only (no embedding anywhere yet)
run("""
    // copy all connections from R4 to the new R4-FINAL, then mark R4 as superseded
    MATCH (old:Result {id: 'R4'})<-[:REPORTS]-(s:Study),
          (old)-[:MEASURES]->(e:Endpoint),
          (old)-[:FOR_POPULATION]->(pop:Population),
          (old)-[:VERSUS]->(cmp:Product),
          (old)-[:EXTRACTED_FROM]->(d:SourceDocument)
    MERGE (new:Result {id: 'R4-FINAL'})
    SET new.text = 'Final analysis of ZEN-302: PASI 75 at week 16 was reached by 82% with Zentrax versus 69% with adalimumab.',
        new.value = 82.0, new.comparatorValue = 69.0, new.unit = '%', new.pValue = 0.002
    MERGE (s)-[:REPORTS {primary: true}]->(new)
    MERGE (new)-[:MEASURES]->(e)
    MERGE (new)-[:FOR_POPULATION]->(pop)
    MERGE (new)-[:VERSUS]->(cmp)
    MERGE (new)-[:EXTRACTED_FROM {page: 9, table: '2a'}]->(d)
    MERGE (new)-[sup:SUPERSEDES]->(old)
    SET sup.reason = 'final analysis', sup.date = date('2026-06-01')
""")
show(consistency_report(), "1. Graph vs pgvector BEFORE sync")      # expect R4-FINAL missing

# 2. Sync pushes the new result's embedding to pgvector
sync()
show(consistency_report(), "2. Graph vs pgvector AFTER sync")       # expect nothing missing

show(search_pg("head-to-head PASI 75 versus adalimumab", category="efficacy", versus="Adalimumab"),
     "3. pgvector retrieval after the update")

#    Pure graph query – it doesn't matter where the vectors were stored.
show(run("""
    MATCH (new:Result)-[:SUPERSEDES]->(old:Result)<-[b:BASED_ON]-(c:Claim)-[:APPEARS_IN]->(sec:Section)
    SET c.status = 'needs_review'
    RETURN c.projectId AS project, c.id AS claim, b.method AS method, old.id AS outdated, new.id AS replacement
    ORDER BY project
"""), "4. Claims needing review")

show(run("""
    MATCH (c:Claim)-[:BASED_ON]->(r:Result)
    WITH r, collect(DISTINCT c.projectId) AS projects
    WHERE size(projects) > 1
    RETURN r.id AS result, projects ORDER BY size(projects) DESC
"""), "5. Evidence reused across projects")

Reset both stores and re-run everything

All scripts are idempotent (MERGE, upserts), so re-running them without a reset won't break anything. But data from earlier runs (for example R1-FINAL, R4-FINAL, extra claims) will change the printed results. To get output that matches this site, reset first. run_all.py does the reset and then runs every module in order:

"""Reset BOTH stores (Neo4j database + pgvector schema), then run every module in order.
Usage:  python run_all.py          # everything
        python run_all.py neo4j    # Neo4j-vector track only (Modules 1-8)
        python run_all.py pg       # pgvector track only (Modules 1-4 + 5P-8P)"""
import subprocess   # starts other programs (here: python on each script)
import sys          # sys.argv = command-line words, sys.executable = path of the current python

# Scripts every track needs, then the two alternative vector tracks.
COMMON = ["s0_check.py", "s1_build_reference.py", "s2_queries.py"]
NEO4J_TRACK = ["s3_embed.py", "s4_vector_search.py", "s5_project_layer.py", "s6_capability_queries.py"]
PG_TRACK = ["s3p_embed_pg.py", "s4p_vector_search_pg.py", "s5p_project_layer_pg.py", "s6p_capability_queries_pg.py"]

# sys.argv[0] is the script name; sys.argv[1] (if given) is the track choice.
track = sys.argv[1] if len(sys.argv) > 1 else "all"
steps = ["reset.py"] + COMMON                      # always start by emptying the Neo4j database
if track in ("all", "neo4j"):
    steps += NEO4J_TRACK
if track in ("all", "pg"):
    # insert reset_pg.py right after reset.py, and append the pgvector scripts at the end
    steps = steps[:1] + ["reset_pg.py"] + steps[1:] + PG_TRACK

for step in steps:
    print(f"\n######## {step}", flush=True)
    # Run each script with the SAME python (so the venv's packages are used).
    # returncode 0 means success; anything else means the script crashed.
    if subprocess.run([sys.executable, step]).returncode != 0:
        sys.exit(f"{step} failed; stopping.")
print("\nAll steps finished successfully.")
