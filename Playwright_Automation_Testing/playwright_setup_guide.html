How it fits together

Five conventions explain the whole repo. The runner, the QC reports and the generators in this guide all build on them.

1

One app = one folder

Each cdp-genai-*-playwright folder is an independent Playwright project with its own package.json, playwright.config.ts and tests/. Its app.config.json registers it with the Live Test Runner.

2

One test case = one file

tests/testcase<id>.ts holds a single test('<id> - <description>', …). The id becomes the runner's button and the description its label. There is no list to update.

3

One .env for everything

The repo-root .env (a copy of example.env) feeds every app through load-env.js: NAME reaches every app, <APP>__NAME only one.

4

Sign in once, reuse it

tests/fixtures.ts opens Chrome or Edge with a persistent profile in .profiles/<channel>, so the SSO session is reused between runs. Because that profile is shared, those suites run with workers: 1.

5

Every run is reported

Playwright writes test-results/results.json, and npm run qc-report turns it into qc-report/index.html. The Live Test Runner does both for you.

Set up & run

Eight steps from a fresh machine to a green test and a QC report. Tick Done as you go: progress is saved in this browser. Commands that mention a folder use the app picked under I'm working on ().

1

Install the prerequisites

⏱ ~10 min · once per machine
  • Node.js 18 or newer. CI and the runner image use Node 22, so use 22 if you can.
  • Git, to clone the repo and contribute.
  • Google Chrome and/or Microsoft Edge. The suites drive the browser installed on your machine (Playwright projects chrome and edge).
  • Corporate network or VPN. Every target app is internal.
  • Optional: VS Code with the Playwright Test for VS Code extension (ms-playwright.playwright) to run and debug tests from the editor.
winget install OpenJS.NodeJS.LTS     # Node.js LTS, includes npm
winget install Git.Git
brew install node git                # macOS; on Linux install Node 18+ with nvm or your package manager

Open a new terminal and check the versions:

node --version                       # v18 or newer (v22 recommended)
npm --version
git --version
⚠️

If npm or npx fails with “running scripts is disabled on this system”, allow local scripts for your account once:

Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned

3

Create your one-stop .env

⏱ 3 min

All settings live in one file at the repo root: the runner's settings and every app's URLs and logins. Every app reads it, whether a test is started from the runner or with npx playwright test in the app folder.

Copy-Item example.env .env
code .env                            # or: notepad .env
cp example.env .env
code .env                            # or any editor

Each line reaches either every app or just one:

Line in .envReachesSeen by the tests as
EMAILID=…every appEMAILID
EMAILID=…only , and it beats the shared lineEMAILID

The prefix is the app id in capitals with - as _, plus two underscores. For it is . The logins for your app look like this:

# Option A: one login for every app
EMAILID=first.last@cepheid.com
PASS=<your password>

# Option B: a login only {{name}} uses (wins over option A)
{{prefix}}EMAILID=first.last@cepheid.com
{{prefix}}PASS=<your password>

The app's URL and other settings are already in .env as commented-out lines in its block. Uncomment one only to override the default.

Which value wins (first match):

  1. The environment picked in the Live Test Runner (from app.config.json, e.g. TEST_ENV=NONPROD).
  2. The repo-root .env: <APP>__NAME, then NAME.
  3. A real environment variable (shell, or the ECS task on the server): <APP>__NAME, then NAME.
  4. The app folder's own .env, if there is one (optional; each app has an example.env listing what it reads).
🔒
.env is gitignored. Never commit it, and never paste passwords into code, tickets or chat.
💡

Leave a setting out rather than empty: NAME= replaces the app's default with an empty string.

The root .env beats shell variables, so $env:NAME='…'export NAME=… does not override a value set in the file. Edit the file instead.

Many apps sign in silently on a Windows-joined laptop (Microsoft account chooser or device SSO), so the password is often only typed on a fresh profile or in the headless server container.

Install the app's dependencies

⏱ 1–2 min per app

Each app folder is its own npm project. Install the one you work on:

cd {{folder}}
npm ci                               # exact versions from package-lock.json

Or install every registered app at once, from the repo root. You need this before running npm run test:browser or hosting the runner:

Get-ChildItem -Directory | Where-Object { Test-Path (Join-Path $_.FullName 'app.config.json') } | ForEach-Object { Write-Host "--- $($_.Name)"; Push-Location $_.FullName; npm ci; Pop-Location }
for d in */; do [ -f "$d/app.config.json" ] && (echo "--- $d" && cd "$d" && npm ci); done
  • npm ci uses the committed package-lock.json. Use npm install only when you change dependencies, then commit the updated lock file.
  • live-test-runner/ has no npm dependencies, so it needs no install.
Next: check the browser →
5

Make sure Playwright can drive Chrome or Edge

⏱ 0–5 min

Tests launch the Chrome (--project=chrome) or Edge (--project=edge) installed on your machine, each with its own test profile. On a standard Windows laptop there is nothing to install. Run these from the app folder, so they match that app's Playwright version:

npx playwright --version             # e.g. Version 1.64.1
npx playwright install chrome        # only if Chrome is missing (Edge: npx playwright install msedge)
npx playwright install chromium      # only for headless, container-style runs
npx playwright --version                     # e.g. Version 1.64.1
npx playwright install --with-deps chrome    # only if Chrome is missing
npx playwright install --with-deps chromium  # only for headless, container-style runs
🖥️
Headless runs (PW_USE_BUNDLED_CHROMIUM=1, see the command builder) use Playwright's bundled Chromium, like the hosted runner container. They keep the chrome/edge project names, but both run on Chromium.
Next: run your first test →
6

Run your first test

⏱ 1–3 min
cd {{folder}}                        # skip if you're already there
npx playwright test --list           # compiles every spec and lists the test cases
npx playwright test testcase1.ts --project=chrome

A Chrome window opens. Most apps use the test profile in /.profiles/chrome: on the very first run you may have to finish the Microsoft sign-in once (on a Windows-joined laptop it is usually silent), and later runs reuse that session. CRA instead signs in a fresh browser through its service-account login. You should see something like:

Running 1 test using 1 worker
  ✓  1 [chrome] › tests/testcase1.ts:… › 1 - … (48.3s)
  1 passed (49.1s)
  • Whole suite: npx playwright test --project=chrome. That takes from a few minutes to about 40 minutes, depending on the app.
  • Several cases: npx playwright test testcase1.ts testcase3.ts --project=chrome. The command builder writes these for you.
⚠️

Run one Playwright run per app at a time. A second run, a codegen window or the Inspector on the same .profiles/<channel> makes Chrome close one of the browsers mid-test.

Some cases create and clean up real records in shared environments (for example, Query Validator cases 2–3 file a tagged chat each run). Read the app's section in README.md before running a full suite.

Next: read the reports →
7

Read the reports

⏱ 1 min
npm run qc-report                    # custom QC report → qc-report\index.html
Start-Process qc-report\index.html
npx playwright show-report           # Playwright's HTML report; Ctrl+C to stop serving it
npm run qc-report                    # custom QC report → qc-report/index.html
open qc-report/index.html            # Linux: xdg-open qc-report/index.html
npx playwright show-report           # Playwright's HTML report; Ctrl+C to stop serving it

The QC report has a Summary of the last run, Latest per Testcase (where every test case stands, including ones the last run skipped), All Testcases & Steps (your // Step comments, ticked off), and one tab per failure with the error, the failed step, a screenshot, a video and a trace.

⚠️
Don't add --reporter=… to the command. It replaces the configured JSON reporter, so test-results/results.json isn't written and npm run qc-report stops with “No test-results/results.json found”.

Failures keep their artifacts under test-results/. To replay one, run npx playwright show-trace test-results/<test-folder>/trace.zip.

Next: try the Live Test Runner →
8

Try the Live Test Runner (optional)

⏱ 2 min

The same web UI the team uses, running on your machine:

cd live-test-runner                  # from the repo root
npm start                            # or: node server.js  →  http://localhost:8090
cd live-test-runner && npm start     # →  http://localhost:8090

Open http://localhost:8090 and sign in with Centralized SSO. Pick an App, an Environment and a Browser, then click a test case, use Run ALL, or type ids such as 2 4 6. Output streams live, and the Playwright and QC reports appear when the run ends.

  • Runner settings (PORT, SSO, Access Manager, roles) are in the same root .env. Restart the runner after you edit it.
  • New apps and test cases appear when you refresh the page. No restart needed.
  • Only one run happens at a time across all apps, because they share browser profiles. Extra runs wait in a queue.

For local development without SSO only, add this to the repo-root .env:

# local development only: never on a shared host, because the runner executes tests on its machine
SSO_AUTH_ENABLED=false

Hosting, roles, the API and the Windows runner agent are covered in live-test-runner/DEPLOYMENT.md.

          Writing good tests
          
      
          Patterns the existing suites already use. Following them keeps tests stable against slow GenAI answers and shared
        environments.
          
      
          
        
          
          
          🎯 Find elements the way users do
          
          
          Role, label and text locators survive styling changes. Avoid long CSS or XPath chains.
          

          page.getByRole('button', { name: 'Save Query' });

          Troubleshooting
          
      
          The problems people actually hit, and how to fix each one.
          
      
      
          
        
          
          npx / npm: “running scripts is disabled on this system”
          
          
            
          PowerShell blocks the npm.ps1 / npx.ps1 shims. Allow local scripts for your account once (or call
              npx.cmd instead):
          

          Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned
          
          
          
        
          
        
          
          npm run qc-report: “No test-results/results.json found”
          
          Run the tests first, without --reporter=…. Overriding the reporter drops the JSON reporter that
            writes results.json. Plain npx playwright test already prints the list output.
          
        
          
        
          
          The browser opens and closes straight away, or “user data directory is already in use”
          
          Another browser is using the same .profiles/<channel>: a second run of the same suite, a
            codegen window, or an Inspector you left open. Close it and run one suite at a time. This is why every app with a shared
            profile sets workers: 1.
          
        
          
        
          
          It asks me to sign in every time, or gets stuck on the Microsoft login
          
          
            
            
              
          • Check <APP>__EMAILID / <APP>__PASS (or the shared EMAILID /
                PASS) in the root .env.
            • 
              
          • Finish the sign-in by hand once in the window the test opened. The profile keeps the session.
            • 
              
          • If the profile is broken, delete it. It is recreated on the next run, and you sign in again:
            • 
            
          

          Remove-Item -Recurse -Force .profiles\chrome     # in the app folder
          

          rm -rf .profiles/chrome                          # in the app folder
          
          
          
        
          
        
          
          My .env change has no effect
          
            
            
          • The root .env beats shell variables and the app folder's own .env. Edit the root
              file.
            • 
            
          • Check the prefix: the app id in capitals, - as _, then two underscores
              (RATE_EXPLORER__).
            • 
            
          • NAME= with nothing after it sets an empty value instead of keeping the default. Delete or comment out the line.
            • 
            
          • Restart the Live Test Runner after editing. A standalone npx playwright test reads the file fresh on each run.
            • 
          
          
        
          
        
          
          My new test case doesn't show up
          
            
            
          • The file must be named testcase<letters or digits>.ts (no -, _ or spaces) and
              sit in the app's tests/ folder.
            • 
            
          • npx playwright test --list in the app folder should list it. If not, the file has a syntax or import error.
            • 
            
          • Refresh the runner page. The hosted runner only updates after the PR is merged to main and deployed.
            • 
            
          • A wrong button label means the title isn't the first test('…') in the file, or it contains a quote.
            • 
          
          
        
          
        
          
          My new app isn't in the App dropdown
          
            
            
          • app.config.json must be valid JSON without a byte-order mark. Windows PowerShell 5.1's
              Set-Content -Encoding UTF8 adds one, and the runner then skips the app. The generator's scaffold script writes
              plain UTF-8.
            • 
            
          • "id" must match ^[a-z0-9][a-z0-9-]*$ and be unique. The runner's console prints
              [apps] skipping <folder>: … with the reason.
            • 
            
          • Hosted runner: the folder must be in the Dockerfile, and the image redeployed (Add a new app, step 5).
            • 
          
          
        
          
        
          
          “Executable doesn't exist at …ms-playwright…”
          
          The browser build for that app's Playwright version isn't installed. Each app folder has its own version.
            In that folder, run npx playwright install chromium for headless runs, or
            npx playwright install chrome if Chrome itself is missing.
          
        
          
        
          
          npm ci: “package.json and package-lock.json are not in sync”
          
          Someone changed package.json without updating the lock file. Run npm install in
            that folder and commit the updated package-lock.json.
          
        
          
        
          
          A test times out waiting for an answer
          
          GenAI answers can take minutes. Raise the budget for that test with test.setTimeout(), and
            the wait itself with expect(…).toBeVisible({ timeout }). Some apps also have a setting for it, such as
            ANSWER_TIMEOUT_MS; see the app's example.env.
          
        
          
        
          
          Running on a Linux machine without a display
          
          Set PW_USE_BUNDLED_CHROMIUM=1 to run headless on bundled Chromium, like the container. Or
            keep headed Chrome and start it under xvfb-run -a.
          
        
          
        
          
          The runner says my run is queued
          
          That's by design. The runner does one run at a time across all apps, because they share one host and its
            browser profiles. Wait for the current run, or cancel it.
