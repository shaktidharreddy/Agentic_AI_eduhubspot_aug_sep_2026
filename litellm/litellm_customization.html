17. Registry setup using the admin console only

For admins who have no shell on the LiteLLM host and no config file access. Everything here is clicks in the console at . Field names below are taken from the running console, not from documentation.

Sign in with your username and password. The default is admin plus the proxy master key—if the yellow Environment-credential login is enabled banner is showing, create a real admin account and set general_settings.disable_env_credential_login: true, because that shared static secret grants full proxy-admin rights to anyone who has it.

Where to find each registry in the left navigation:

Registry Navigation
Models Models + Endpoints → Add Model
Auto router Models + Endpoints → Auto-Routers (Beta)
Credentials Models + Endpoints → LLM Credentials
MCPMCP Servers
A2AAgentic → Agents
MemoryAgentic → Memory
Web searchTools → Search Tools
Vector storesTools → Vector Stores
Skills (marketplace)Skills

Everything created here is stored in the database, so it survives restarts and stays editable. Entries that came from config.yaml show Source: config and are read-only in the console.

17.1 Models

Models + Endpoints → Add Model

Worked example—registering the Azure deployment gpt-5.6-luna:

Field Value to enter
Provider Azure (the literal entry; not “Azure OpenAI”)
LiteLLM Model Name(s)gpt-5.6-luna
ModeChat - /chat/completions
Existing Credentialsleave empty if filling the fields below
API Base
API Version2024-10-21
Base Modelleave empty—see the warning
Azure API Keyyour Azure key
Model Access Groupoptional, e.g. platform-team

Enter the deployment name in LiteLLM Model Name(s). The form states: “Your deployment name will be saved as the public model name, and LiteLLM will use azure/deployment-name internally”—so developers will call gpt-5.6-luna and LiteLLM resolves azure/gpt-5.6-luna. The Model Mappings table below the field previews that pairing as you type; check it before saving.

Finish with Test Connect, then Add Model. Confirm under Deployed Models.

Leave Base Model empty unless you are certain. It exists for cost tracking when the deployment name hides the real model. A wrong value makes LiteLLM apply the wrong parameter rules—a reasoning model labelled azure/gpt-4.1 gets max_tokens forwarded and Azure rejects the call. With two deployments under one public name that becomes an intermittent failure, because only the mislabelled half fails.

For a second deployment of an existing model, enter the same public name; the two rows become one load-balanced group. Two rows you did not intend is the single most common cause of “it works sometimes”.

17.3 Auto router

Models + Endpoints → Auto-Routers → Add Auto Router

Worked example—the five-tier router used by this stack:

Field Value to enter
Auto Router Namecepheid_smart_router
Model Access Groupoptional
Choose your classifier Decisions Model (a decision model picks the tier)
How often to classifyEvery request
Simple Tiergpt-5.6-luna, reasoning effort Default
Medium Tiergpt-5.6-terra, reasoning effort Default
Complex Tiergpt-5.6-sol, reasoning effort Default
Reasoning Tiergpt-5.6-sol, reasoning effort xhigh
Add a non-reasoning tiergpt-4.1-nano
Default Modelgpt-5.6-luna

Classifier choices are Heuristics (local, no API call), LLM (a judge model), or Decisions Model. Classification frequency is Every request, Every new user message, or Once per session.

Use Test Routing with representative prompts before saving, then Add Auto Router. The list view shows Type, Routes to and Default model, which is the fastest way to spot an empty tier.

Put an ordinary chat model on the non-reasoning tier—it serves relay, acknowledgement, reformatting and extraction. A classifier model cannot serve those requests at all, and a reasoning model there can return an empty body, because the router injects the tier’s token ceiling and the model spends it on reasoning. Test Routing shows which tier answered but not that the answer was blank, so read the response text too.

17.4 MCP servers

MCP Servers → + Add New MCP Server → + Custom Server

The first screen is a catalogue of known public servers. Your internal server is behind + Custom Server at the top left—easy to miss.

Worked example—the calculator server from section 4:

Field Value to enter
MCP Server Namecalc_http
Alias calc_http (prefixes tool names, e.g. calc_http-add)
DescriptionFastMCP Calculator over streamable HTTP
Logo / GitHub Source URLoptional, cosmetic
Transport TypeStreamable HTTP (Recommended)
MCP Server URL

MCP Access Groupsoptional

Transport choices are Streamable HTTP (Recommended), Server-Sent Events (SSE), Standard Input/Output (stdio) and OpenAPI Spec. The MCP Server URL field only appears after you choose a transport.

Add MCP Server, then check the card shows Healthy. Unhealthy means the gateway cannot reach the URL you typed—it must be routable from the LiteLLM host, so 127.0.0.1 only works if the server runs on that same box.

The Connect tab generates client configuration for developers, and Import from JSON accepts a standard MCP client config block if you have one.

17.5 Vector stores

The page has two flows and picking the wrong one is the usual mistake:

  • Create Vector Store—uploads documents and creates a new store.
  • Manage Vector Stores → + Add Vector Store— registers a store that already exists. This is the one for a self-hosted backend.

Provider choice has a consequence the form never explains:

Provider API Base field? Console document upload
PostgreSQL pgvector (LiteLLM Connector) Yes, on the form No
OpenAI No—only via a credential Yes

The console’s drag-and-drop upload uses the RAG ingest path, which accepts only certain providers, and pg_vector is not one of them. So for a self-hosted OpenAI-compatible backend, register it as OpenAI and supply the base URL through the credential from 17.2.

Worked example—registering the existing genai-kb store:

Field Value to enter
ProviderOpenAI
Vector Store ID 6ad5a50a-8829-4134-86e4-623fe516d5b6 (from your backend)
Vector Store Namegenai-kb
DescriptionInternal runbooks and handbooks
Existing Credentials pgvector-sidecar (created in 17.2)
Metadata optional, e.g. {"owner": "platform"}

Create. The row should show Provider: OpenAI and Source: DB.

Then use Create Vector Store to drag documents in, and Test Vector Store to run a query against it. Picking PostgreSQL pgvector instead still gives working search—you lose console uploads and must ingest over the API.

Agent Type choices include A2A Standard, LangFlow, LangGraph, Bedrock AgentCore, Azure AI Foundry, Pydantic AI, Vertex AI Agent Engine, watsonx Orchestrate and Custom / Other. Identity Provider offers No explicit identity binding or Microsoft Entra ID.

17.9 Skills

Skills → + Add Skill

This page manages the Claude Code marketplace, served at /claude-code/marketplace.json. It registers a source reference, not an upload.

Worked example—the pptx skill already registered on this gateway:

Field Value to enter

Description (Optional)Create and edit PowerPoint decks

Two caveats before you plan around this page. The Source URL must be reachable over HTTPS by whoever consumes the marketplace, so an internal-only git host will not work. And this is not the registry a chat request uses via container.skills—those are zip archives containing SKILL.md, they have no console page, and they can only be registered over the API. Registering here does not make a skill available to container.skills, or vice versa.

What you cannot do from the console

Worth knowing before promising a fully click-only workflow:

  • Agent-skills archives (container.skills)—upload is API-only, as above.
  • Config-file entries—anything from config.yaml is read-only in the console. To change it you need file access and a restart.
  • A self-hosted vector store with a custom base URL— possible, but only via the credential indirection in 17.5, not from the vector store form alone.

16. Registry reference—admin setup and developer usage

Eight registries live on the gateway. This section is the quick reference: what each one is, how an admin registers an entry, and how an end developer consumes it. Every request below was run against this gateway.

Two conventions throughout:

export LITELLM_BASE=
export LITELLM_KEY=sk-...          # a virtual key for developers, master key for admins
Registry Admin writes Developer calls Console
Models model_list / POST /model/new POST /v1/chat/completions Models + Endpoints
Auto router POST /model/new (DB only) model: "<router name>" Models + Endpoints
MCP mcp_servers / POST /v1/mcp/server /mcp or /mcp-rest/tools/* MCP Servers
A2A agents / POST /v1/agents POST /a2a/{name}/ Agentic → Agents
Vector stores POST /vector_store/new POST /v1/vector_stores/{id}/search Tools → Vector Stores
Web search search_tools in config POST /v1/search/{name} Tools → Search Tools
Memory n/a (self-serve) POST/GET/PUT/DELETE /v1/memory Agentic → Memory
Skills POST /v1/skills (zip) container.skills Skills

Anything registered over REST lands in the database and is editable in the console. Anything in config.yaml is read-only there, and if a name exists in both, the database record wins.

16.1 Models registry

Admin. Config file, applied on the LiteLLM host: 

model_list:
  - model_name: gpt-5.6-luna            # the name developers use
    litellm_params:
      model: azure/gpt-5.6-luna          # the real deployment
      api_base: os.environ/AZURE_API_BASE
      api_key: os.environ/AZURE_API_KEY

Or over REST, no restart:

curl -X POST $LITELLM_BASE/model/new -H "Authorization: Bearer $LITELLM_KEY" \
  -H 'Content-Type: application/json' -d '{
    "model_name": "gpt-5.6-luna",
    "litellm_params": {"model": "azure/gpt-5.6-luna", "api_key": "...", "api_base": "..."}
  }'

Do not set base_model unless the deployment name hides the real model. A wrong value makes LiteLLM apply the wrong parameter rules— a reasoning model labelled azure/gpt-4.1 gets max_tokens forwarded and Azure rejects it. With two deployments under one model_name, load balancing turns that into an intermittent failure. Check for duplicates with GET /v1/model/info and compare max_output_tokens.

Developer.

import os
from openai import OpenAI

client = OpenAI(base_url=f"{os.environ['LITELLM_BASE']}/v1",
                api_key=os.environ["LITELLM_KEY"])

resp = client.chat.completions.create(
    model="gpt-5.6-luna",
    messages=[{"role": "user", "content": "Summarise this incident in two lines."}],
)
print(resp.choices[0].message.content)

16.2 Auto router registry

Routes each request to the cheapest adequate model tier, classified per request.

Admin. The router is a model whose litellm_params.model is auto_router/complexity_router: 

curl -X POST $LITELLM_BASE/model/new -H "Authorization: Bearer $LITELLM_KEY" \
  -H 'Content-Type: application/json' -d '{
    "model_name": "cepheid_smart_router",
    "litellm_params": {
      "model": "auto_router/complexity_router",
      "complexity_router_config": {
        "classifier_type": "jev",
        "classification_mode": "every_request",
        "default_model": "gpt-5.6-luna",
        "enable_non_reasoning_tier": true,
        "tiers": {
          "NON_REASONING": ["gpt-4.1-nano"],
          "SIMPLE":        ["gpt-5.6-luna"],
          "MEDIUM":        ["gpt-5.6-terra"],
          "COMPLEX":       ["gpt-5.6-sol"],
          "REASONING":     ["gpt-5.6-sol"]
        }
      }
    }
  }'

Three things that cost real time:

  • NON_REASONING is a serving tier, not the classifier. It handles relay, acknowledgement, reformatting and extraction, so it needs a real chat model. Putting the classifier model there fails every request routed to it.
  • Don’t put a reasoning model on a tier while max_tokens_from_tier_model is at its default true: the router injects the tier ceiling as max_tokens, and a reasoning model can spend the whole budget on reasoning and return HTTP 200 with empty content—a silent failure.
  • POST /model/update rejects partial updates. Round-trip the full litellm_params from GET /v1/model/info. Safe only when the object has no api_key—keys come back masked and would be written back as literal ****.

Developer. Call it like any model; you cannot pin a tier from the client. x-litellm-model-id returns the deployment id, so map it back to see which tier answered: 

raw = client.chat.completions.with_raw_response.create(
    model="cepheid_smart_router",
    messages=[{"role": "user", "content": "Return only the order id: order_id=A-1193"}],
)

rows = httpx.get(f"{base}/v1/model/info",
                 headers={"Authorization": f"Bearer {key}"}, timeout=60).json()["data"]
names = {m["model_info"]["id"]: m["model_name"] for m in rows}

print(names.get(raw.headers.get("x-litellm-model-id")))   # gpt-4.1-nano
print(raw.parse().choices[0].message.content)             # A-1193

If you need a specific model, call that model directly instead of the router. Note that max_tokens you pass may be overwritten by the tier ceiling while max_tokens_from_tier_model is true.

16.3 MCP registry

Admin.

mcp_servers:
  calc_http:
    url: 
    transport: http
    description: FastMCP Calculator over streamable HTTP
curl -X POST $LITELLM_BASE/v1/mcp/server -H "Authorization: Bearer $LITELLM_KEY" \
  -H 'Content-Type: application/json' -d '{
    "server_name": "calc_http", "alias": "calc_http", "transport": "http",
    "url": ""
  }'

curl -s $LITELLM_BASE/v1/mcp/server/health -H "Authorization: Bearer $LITELLM_KEY"

Bind MCP servers to a routable interface, not 127.0.0.1, or the gateway cannot reach them. Verify health before telling anyone it is registered.

Developer—MCP-native client. The gateway is itself an MCP server: 

                  # all permitted servers
        # one server

Pass the key as the bearer token; x-mcp-servers narrows the toolset.

Developer—plain REST.

import httpx, os

base, key = os.environ["LITELLM_BASE"], os.environ["LITELLM_KEY"]
h = {"Authorization": f"Bearer {key}"}

with httpx.Client(base_url=base, headers=h, timeout=60) as c:
    servers = c.get("/v1/mcp/server").json()
    server_id = next(s["server_id"] for s in servers
                     if (s.get("alias") or s["server_name"]) == "calc_http")

    tools = c.get("/mcp-rest/tools/list").json()

    out = c.post("/mcp-rest/tools/call", json={
        "name": "add",                 # UNPREFIXED name
        "arguments": {"a": 21, "b": 21},
        "server_id": server_id,        # required
    }).json()
    print(out["content"][0]["text"])   # 42

Tool names are {alias}-{tool} when listed through the gateway’s catalog, but /mcp-rest/tools/call wants the unprefixed name plus server_id.

16.4 A2A registry

Admin.

curl -X POST $LITELLM_BASE/v1/agents -H "Authorization: Bearer $LITELLM_KEY" \
  -H 'Content-Type: application/json' -d '{
    "agent_name": "weather-agent",
    "agent_card_params": {
      "name": "Weather Agent",
      "description": "Reports the current weather for a city.",
      "url": "",
      "protocolVersion": "0.3",
      "skills": [{"id": "weather", "name": "Weather lookup",
                  "description": "Current conditions for a city",
                  "tags": ["weather"]}]
    }
  }'

Always pin protocolVersion, advertise a routable URL (not 127.0.0.1), and include skills—omitting them stores a generic “chat” skill, which is the text /v1/agents/search embeds, so semantic routing ranks on the wrong description.

Developer. A2A is JSON-RPC over HTTP:

import httpx, os, uuid

base, key = os.environ["LITELLM_BASE"], os.environ["LITELLM_KEY"]

payload = {
    "jsonrpc": "2.0", "id": str(uuid.uuid4()), "method": "message/send",
    "params": {"message": {"role": "user", "kind": "message",
                           "messageId": str(uuid.uuid4()),
                           "parts": [{"kind": "text", "text": "Weather in Paris?"}]}},
}

# follow_redirects is REQUIRED: /a2a/{name}/ answers 307 and a client that drops
# the body on redirect makes every agent look broken.
with httpx.Client(headers={"Authorization": f"Bearer {key}"},
                  follow_redirects=True, timeout=180) as c:
    r = c.post(f"{base}/a2a/weather-agent/", json=payload).json()

parts = r["result"].get("parts") or r["result"]["status"]["message"]["parts"]
print("".join(p.get("text", "") for p in parts))

Discover agents first if you don’t know the name:

curl -s "$LITELLM_BASE/v1/agents/search?query=who+can+convert+currency" \
  -H "Authorization: Bearer $LITELLM_KEY"
curl -s $LITELLM_BASE/a2a/weather-agent/.well-known/agent-card.json \
  -H "Authorization: Bearer $LITELLM_KEY"

16.5 Vector store registry

Deployment is section 15; this is the registry contract.

Admin.

curl -X POST $LITELLM_BASE/vector_store/new -H "Authorization: Bearer $LITELLM_KEY" \
  -H 'Content-Type: application/json' -d '{
    "vector_store_name": "genai-kb",
    "vector_store_description": "Internal runbooks and handbooks",
    "vector_store_id": "6ad5a50a-...",
    "custom_llm_provider": "openai",
    "litellm_params": {"api_base": "",
                       "api_key": "..."}
  }'

The store must already exist on the backing service—LiteLLM registers an id, it does not create one. Use openai, not pg_vector, and end api_base with /v1 (section 15.4 explains why).

Developer—search.

hits = httpx.post(f"{base}/v1/vector_stores/{store_id}/search",
                  headers={"Authorization": f"Bearer {key}"},
                  json={"query": "what counts as a Sev1?", "max_num_results": 3},
                  timeout=120).json()["data"]

for h in hits:
    print(round(h["score"], 3), h["filename"], h["content"][0]["text"][:120])

Developer—ingest. Use pgvector-service/ingest.py, or call the endpoint directly. The JSON goes in a form field named literally request: 

curl -X POST $LITELLM_BASE/v1/rag/ingest -H "Authorization: Bearer $LITELLM_KEY" \
  -F 'request={"ingest_options":{"vector_store":{"custom_llm_provider":"openai","vector_store_id":"6ad5a50a-..."},"wait_for_ingestion":true}}' \
  -F 'file=@runbook.md;type=text/markdown'

A 200 does not mean success—read status in the body, which is completed or failed.

16.7 Memory registry

Durable key/value context on the proxy, scoped to the caller’s user or team. There is no admin registration step—developers create their own entries, and an admin can scope one to another user or team with user_id/team_id.

Developer.

h = {"Authorization": f"Bearer {key}", "Content-Type": "application/json"}

httpx.post(f"{base}/v1/memory", headers=h, json={
    "key": "crm/acct-42/preferences",
    "value": "Prefers metric units. Escalate Sev1 to the platform rota.",
    "metadata": {"account": "acct-42"},
})

httpx.put(f"{base}/v1/memory/crm/acct-42/preferences", headers=h,
          json={"value": "Prefers metric units."})

row = httpx.get(f"{base}/v1/memory/crm/acct-42/preferences", headers=h).json()

page = httpx.get(f"{base}/v1/memory", headers=h,
                 params={"key_prefix": "crm/", "page": 1, "page_size": 50}).json()
print(page["total"], len(page["memories"]))

httpx.delete(f"{base}/v1/memory/crm/acct-42/preferences", headers=h)

Keys are path-like namespaces, so key_prefix is the cheap way to list a tenant’s entries. Feed value into a prompt yourself—nothing is auto-injected.

16.8 Skills registry

A skill is an Anthropic Agent Skills archive: a zip with SKILL.md at its root, injected as model instructions when a call references it.

Admin. multipart/form-data, and custom_llm_provider=litellm_proxy is mandatory—without it the request is proxied to Anthropic and needs an Anthropic key: 

zip -j postmortem.zip skills/blameless-incident-postmortem/SKILL.md

curl -X POST "$LITELLM_BASE/v1/skills?custom_llm_provider=litellm_proxy" \
  -H "Authorization: Bearer $LITELLM_KEY" \
  -F 'display_title=Blameless Incident Postmortem' \
  -F 'description=House format for incident postmortems' \
  -F 'files[]=@postmortem.zip;type=application/zip'

curl -s "$LITELLM_BASE/v1/skills?custom_llm_provider=litellm_proxy" \
  -H "Authorization: Bearer $LITELLM_KEY"

Only the archive reaches the model. The description field is stored for discovery but never injected, so the guidance must live in SKILL.md.

Developer.

resp = client.chat.completions.create(
    model="claude-sonnet-4",            # see the caveat below
    messages=[{"role": "user", "content": "Write the postmortem for INC-1182."}],
    extra_body={"container": {"skills": [
        {"type": "litellm_skill", "skill_id": "litellm_skill_72249ab3-..."}
    ]}},
)

Requires an Anthropic-family model. The skill is converted into an Anthropic-shaped tool (name/description/input_schema). Against an Azure or OpenAI deployment the call fails with 400 Missing required parameter: 'tools[0].type'. Registration and listing work regardless; only invocation is provider-bound. If the gateway has no anthropic/… or bedrock/anthropic.… model, this path is unusable—paste SKILL.md into the system prompt instead.

Skills shown under Skills in the console come from a different registry—the Claude Code marketplace at /claude-code/plugins, which stores a git source reference rather than an archive. Registering one does not register the other.
